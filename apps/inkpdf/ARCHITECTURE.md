# InkPDF architecture

A fast, pen-first PDF annotator for Windows, Linux and Android (see `docs/PORTING.md`; everything below the adapters is shared). The application layer was rewritten in 0.2.0 from the plan
below; the 0.1.11 source is in this repository's history. The layering rule and the tool contract are
enforced by tests (`src/architecture.rs`, `src/editor/tests/contract.rs`).

## What was wrong with 0.1.x

| Smell | Where | Principle broken | Now |
|---|---|---|---|
| `Editor` was one 40-field struct doing routing, every tool, selection, text, drafts, prompt, toolbar | `editor/` | **S** | tools own their state; `Editor` routes and owns the window's chrome |
| `match self.tool` / `if tool == Text` in ~15 places; a new tool edited all of them | `pen.rs`, `mouse.rs`, … | **O** | one `ToolSet` match; everything else calls the `Tool` trait |
| One shared `Act` enum for every tool's gesture; the renderer inspected it to paint overlays | `act.rs`, `ink_layer.rs` | **O**, **D** | each tool has a private gesture enum and paints itself through `Painter`; `Act` is only the chrome's |
| Device rules scattered as `if`s | `pen.rs`, `mouse.rs` | **S**, **O** | `Tool::policy()` returns `InputPolicy` (data); one routing function reads it |
| Public `want_*` flags the shell polled and reset | `Editor` | **I** | `Request` queue the shell drains |
| Tests reached into `Editor` internals | `editor/tests` | **D** | tests use accessors (`ed.draft()`, `ed.tools.shape.controlling()`) |

## Layers (dependencies point inward only)

```
 adapters  ─────────►  session  ─────────►  tools  ─────────►  domain
 app (winit shell),     editor/ (Editor:     tools/ (Tool trait,  ink, figure, geometry, smooth,
 gpu, platform,         routing, chrome,     Pen, Shape, Text,    text, laser, view, colour, links,
 doc                    history, prompt)     Pointer, gestures)   workspace, requests, input
```

* **domain** — no window, GPU, file or clock. `workspace.rs` is the document state the tools share
  (ink, selection, view, layout, styles, redraw flag); `requests.rs` is the queue of asks to the shell.
* **tools** (`src/tools/`) — `Tool` trait (`policy`, `pointer`, `owns`, `busy`, `end`, `settle`, `leave`,
  `cancel`, `key`, `undo`, `redo`, `restyled`, `drag_offset`, `paint`); `PenTool`, `ShapeTool` (with
  `anchors` and `draft` modules), `TextTool`, `SelectTool`, `PickTool` (the lasso and the eraser: the same type, which of the two a press is
  decided by `Workspace::role`); shared gesture parts in `gestures.rs`
  (`Mover`, `Eraser`, `Lasso`); `paint.rs` (`Painter` trait and line helpers). A tool never names another
  tool, the toolbar, the editor, the window or the GPU.
* **session** (`src/editor/`) — `Editor` is the facade the shell talks to. `routing.rs` hands pointer
  and keyboard input to the tool in use according to its policy and exposes read accessors; `pen.rs`,
  `mouse.rs`, `touch.rs`, `navigation.rs` do the window's own work (toolbar presses, panning, links,
  pull-for-a-page); `toolbar_ui.rs`, `cursor.rs` (which cursor, from `input::decide`), `reader.rs` (the reader's keys and zoom), `pills.rs` (the pills that fold into round buttons in a narrow window), `prompt.rs`, `commands.rs`, `select.rs` are chrome and history.
* **adapters** — everything touching the OS. The session knows winit's event *types* (the vocabulary of
  input) but never the window, GPU, files or the pointer layer.

### The layers, as enforced (`src/architecture.rs`)

Every top-level module has a layer, and the tests read the sources (production lines only, whatever the position of
the `#[cfg(test)]` items) to check the real module graph against this table. A module may use its own layer and the
ones below; no two modules may reach each other, directly or through others.

| Layer | Modules |
|---|---|
| adapter | `app`, `gpu`, `platform`, `pdf`, `doc`, `renderer`, `path_store`, `pdf_read`, `ink_io`, `tiles`, `thumbnail` |
| session | `editor` |
| tools | `tools` |
| ui | `toolbar` |
| domain | `tool`, `input`, `field`, `requests`, `workspace`, `selection`, `settings`, `store` |
| model | `figure`, `form`, `ink`, `laser`, `links`, `outline`, `pages`, `page_table`, `pagetext` |
| base | `plane`, `motion`, `scene`, `clock`, `geometry`, `colour`, `coords`, `view`, `text`, `smooth`, `clipboard`, `palette` |

* `plane` holds the point type `P` and the plane arithmetic (distances, polygon tests, simplify, thin, `clamp_into`)
  that `ink`, `figure`, `smooth`, `text` and `laser` all stand on; `ink` re-exports the common ones. `geometry` is only
  the `Shape` enum; the polyline a shape makes is `figure::shape_points`. `figure::NodeAction` is what can be done to
  a point of a shape. None of these depend on anything above them, which is what removed the cycles
  `ink`/`figure`/`geometry` and `toolbar`/`selection`/`workspace`/`requests`.
* `tool` holds which tool is in use (`Tool`), how each writes (`ToolStyle`), the colour slots and the thickness ranges,
  and `requests` holds `Choice`, the answer to the unsaved-changes prompt: plain data that the document state, the saved
  settings and the toolbar all use, so none of the first two reaches into the toolbar any more.
* There are no upward edges and no cycles left: `KNOWN_EXCEPTIONS` in the test is empty, and an edge that points up has to be
  added there, with a reason, or fixed.
* `scene` holds what is drawn as plain data (round-ended lines and rounded rectangles); the toolbar and the tools describe
  what they want in it and `gpu` draws it. `clock` is the performance-counter clock; the editor takes it as a function
  (`Editor::set_clock`), so tests can give it another.

2. The `ink`/`figure`/`geometry` and `toolbar`/`selection`/`workspace` cycles (the base module `plane`).
3. `Tool`, `ToolStyle`, the palette and the ranges moved out of `toolbar` (into `tool`), and `Choice` (into `requests`).
4. `toolbar` describes what it draws in `scene` types, which `gpu` draws; it no longer knows `gpu`.
5. The tools share what they have in common:
   * `tools::gestures::Pick` is erase / select by loop or tap / drag the selection, which the pen, shape and text tools
     each used to carry their own copy of;
   * `Tool::actions`, `action_enabled` and `act` let a tool offer buttons of its own to the bar (`ToolAction`), so the bar
     does not know that shapes have points;
   * `tool::Tool` carries what is true of each tool (`ALL`, `kind`, `makes_items`, `name`), and `Kind` lives beside it.
6. The editor:
   * the window's own controls are `editor::Chrome` (the prompt, the panel and its colour editor, the hover, the press under
     way), whose small state machines take the document state as an argument; the `Editor` routes input and owns one;
   * `Editor` derefs to the document state read-only outside tests, so only the editor and the tools change it, and the
     shell asks for changes in the editor's terms (`set_dpr`, `document_saved`, `requests()`, ...);
   * the editor reads the time from its own clock, not from the pointer layer.
### Save As and Open

The system's own file dialogs (`platform/dialog.rs`: Windows' and, through the desktop portal, Linux's; Android's is an `Intent`, see
`platform/saf.rs`). A dialog blocks until it is answered, so `Platform::pick` opens it on a thread of its own, over the window, starting in
the folder the document is in (else Documents) and offering its name; the answer waits to be taken by `Platform::take_picked` (the shell is
woken through the `Waker` it gave `set_waker`) and is a `Picked`, the same on every platform. `app/files.rs` keeps what was waiting on a
save (`Then`) across the dialog.

### Platforms (`src/platform/`)

Everything that differs by operating system is behind `platform/mod.rs`, chosen at compile time. The shell holds one
`Box<dyn Platform>` (built by `platform::native()`): where documents go (`documents_dir`, `config_dir`, `file_store`), the
system font if its widths are the ones PDF readers use (`system_font`: Arial on Windows, nothing elsewhere, where the built-in
Liberation Sans is used), what the user asked of motion and the machine's posture (`motion_prefs`, `detect_mode`), side effects
(`open_url`, `error_box` where the system has one, else a card of the program's own over the page: `has_error_box`; `set_text_input`, and on a phone `keyboard_covered`,
how much of the window the soft keyboard covers; `clipboard`) and the pen reader (`install_pointer`). The window crosses the seam as a
`raw-window-handle` plus a `Waker`, so no windowing toolkit type is in the API. `platform::fake::FakePlatform` runs the shell's calls
with no OS. Process-level calls before there is a window (`attach_parent_console`, `report_fatal`) stay free functions.

* `windows/`: Win32 pointer messages with the history Windows batches (`pointer.rs`), message boxes, clipboard and fonts (`native.rs`),
  posture, the known folders, and the performance counter converted to the app's clock (`counter.rs`).
* `linux/`: `tablet.rs` is the pen on Wayland (a second event queue on winit's own connection, `zwp_tablet_v2`, read in `pump`; winit's touches are handed
  through `late_touch`), over `tablet_frames.rs`, a pure state machine from the protocol's frames to `PointerEvent`s that is tested on every OS, and
  `tablet/fake_compositor.rs`, a compositor of our own that tests the binding over a socket pair; `clipboard.rs` is arboard's; `mod.rs` the desktop's
  settings (`gsettings`: the look, the animations). X11 reads the pen as the mouse (`install_pointer` says why not).
* `android/`: `reader.rs` reads the activity's input queue *before* winit (which flattens every `MotionEvent` into a plain touch) and
  hands the fields to `motion_event.rs`, a pure decoder tested on every OS: tool type, pressure, the stylus's buttons, hover, the points
  between events, cancels. Pointers are told by device *and* id (a pen digitiser and a touch screen both count from 0).
* `unix_dirs.rs` (folders by the XDG rules), `stubs.rs` (services with nothing behind them yet).

The pen reader is a `PointerSource`: `pump` (take what the OS has queued, right after the display wait), `pending`, `drain_into`
(append `PointerEvent`s with the OS's batched `samples` to a buffer the shell keeps, so nothing is allocated per frame),
`take_posture_change`, `set_scale` (the window's scale, for a source that reads logical pixels), `uninstall`. A new OS adds one such source and changes nothing above `platform`; the session may not name it
(tested), and a contract suite (`platform/contract.rs`) holds every source to the same rules. The layering test also says nothing below the
adapters touches a file, the environment, an OS, a PDF crate, `wgpu` or `winit`: what they need (a font, the settings folder, the
clock's source) is handed to them.

### Storage and the PDF

* `store.rs` (domain) is the port: `DocId` (a path, or an address a platform made, such as an Android `content://` URI) and the
  `FileStore` trait (`read`, `write_atomic`). `path_store.rs` (adapter) is the file system behind it: the atomic save (written
  beside the old file and swapped in) and the read-only refusal.
* `doc.rs` is the renderer's pool and the saved bytes; it reads and writes only through a `FileStore`. The pure bookkeeping of the pages
  (their size and geometry, which page of the renderer's file draws each, copies, and the deleted pages kept for undo) is `page_table.rs`
  (model), tested with no PDF.
* `pdf/` (adapter) is **the one seam to the PDF engine**: `PdfBackend` (inspect, blank, open, a render pool, one render now, page text,
  dates) and `PdfDocument` (an open file: links, outline, annotations, add and delete annotations, organize pages, save whole or as an
  update). Its types are the program's own (`RenderRequest`, `Rendered`, `RawLink`, `Annotation`, `NewAnnotation`); the only
  implementation is `pdf/pdfcraft.rs`, and `architecture.rs` fails if any other module names `pdfcraft_*` or `hayro`. `pagetext.rs` (model)
  is the trait for one page's text (`PageTextView`) that the text tools will use; the pdfcraft side implements it. `pdf::native()` is the
  backend the program was built with. `pdf/contract.rs` is the conformance suite (geometry, sizing, text and find, outline and links, annotations
  written and read back, organized pages, renders checked by a few pixels, a render pool, damaged files): a backend must pass it, and a test
  shows it can fail. The upgrade rule, the numbers and the criteria for reconsidering the engine are in `docs/PDF-BACKEND.md`.
* `ink/` is four parts held together by the `InkStore` facade: `drawing.rs` (the strokes and the pages that changed: the one thing a step changes),
  `history.rs` (the steps, `Cmd`, which know how to apply and revert themselves, and the `History` that runs them), `query.rs` (what can be asked
  of the strokes without changing them) and `store.rs` (the ids, the counts of changes, and the public API of one-step edits).
* `Doc` (`doc.rs`) is the file model: its pages (`PageTable`), the file as last written, and saving. What a file holds besides its pages comes
  out of `open` once, as `Contents` (ink, links, form, outline), and what a save writes besides the ink goes in per call, as `ink_io::Extras`; the
  document keeps no staged state. The pictures are `Renderer` (`renderer.rs`: the pool, its queue and the look), which knows the file it renders
  from and not the document's pages. The PDF engine is a value the document is opened with (`Doc::open_with`), not looked up inside `ink_io`.
  Opening and saving fail with `DocError`.
* The window's own cards (the bar under the tools, the search card, the round button under the theme button) share one press path: `card_at`
  says which button is under a point, `Act::Card` holds a press on any of them, and `activate_card` does what it asks. A new card is a `CardHit`
  variant and three arms, not a new `Act` variant in every list of them. `Workspace` keeps what the tools write with in `styles`, how the interface
  looks in `look` and what was copied in `clip`.
* A frame is asked for by hand (`redraw = true`), so `stress/redraw.rs` feeds random input and checks the rule that makes that safe: whenever
  what is drawn is different after an event, a frame was asked for.
* `pdf_read.rs` (adapter) places what the engine hands over on the layout (links in document space, an outline with tidy titles) for the
  model, which (`links.rs`, `outline.rs`) keeps it and carries it through edits. `ink_io.rs` is the policy for ink: which annotations are
  ours (`inkpdf-` names), how strokes and shapes are written, in terms of `PdfDocument`.

### The shell (`src/app/`)

`State` is the window, the GPU, the editor and the platform, with three plain groups of what the shell keeps (fields, not objects, so
nothing sits on the frame path): `FrameLoop` (the clock, statistics, what the loop waits for), `DocumentSession` (the open document, its
store, what waits on the unsaved-changes prompt and on Save As) and `UiLayers` (what is on the GPU and what it was built from). The
presenters that turn editor state into GPU data (`ink_layer`, `text_layer`, `overview`, `pages`) are methods of `UiLayers`; they take a
`Paint` (the editor, the GPU, the document, the frame number) built by `paint!(self)`. `files.rs` is the document workflow
(`Then`, open, save, close, serving the editor's `Request`s). `--record FILE` copies every event given to the editor (`replay.rs`,
`input/record.rs`, a text line each) and `--replay FILE` plays a recording back at its pace. `--inject FILE` gives the editor, as they are
appended to the file, lines in the same format, stamped with the moment (the real-input checks use it where the system has no stylus or finger to
send); `--layout FILE` keeps where every control is and the page, page count, unsaved mark and mode (`layout.rs`).

## Pages: one edit, everything follows

Before the pages overview a page edit was done six times, by hand, in `doc.rs`, `ink/store.rs`, `ink_io.rs`, `app/files.rs`,
`editor/mod.rs` and `requests.rs`, and the page layout was kept twice (the document's and the editor's) and synced by the
shell in a fixed order. Now:

* **`pages.rs`** holds the one value, `PageEdit` (`Insert`, `Delete { grave }`, `Move`, `Arrange`, `Duplicate`, `Restore { grave }`),
  and the one rule, `PageEdit::order` (which page each page of the result was). `apply`/`apply_with` carry any list kept by page
  through an edit; `Layout::edited` is the layout after it; a `Remap` says where each page went, how far its place moved, and
  which pages are copies. `inverse` is the edit that undoes it. Pure arithmetic, tested for every variant and for all inverses.
* **The editor does every page edit** (`editor/pages.rs`, `Editor::edit_pages`): it ends what was under way, computes the
  remap, hands it to the ink store as **one step of the history** (`Cmd::Pages`: the forward and backward remaps, the strokes
  that were buried, the strokes made for copies), carries the links (`links::remap`/`copies`/`restore`) and the outline
  (`outline::remap`/`restore`), keeps what a deletion took in a grave, brings the selection and the view along, and asks the shell
  once (`Request::PagesEdited(edit)`). Undo and redo of such a step come back through the same follow-up
  (`InkStore::take_page_edit` → `Editor::page_step_followed`).
* **One linear history, so no old step is ever renumbered.** An older step is undone only after the page edit above it, when
  the pages are numbered as they were when it was recorded.
* **The shell** applies the same edit to the file's page table (`Doc::apply`: sizes, geometry, and a slot per page saying which
  page of the renderer draws it and which page of the file it is, or is a copy of) and drops what was drawn for renumbered
  pages. `Doc` no longer keeps a layout (it computes one) nor the links (the editor owns them).
* **Saving** (`ink_io::save`) makes the file's pages the document's: copies are appended first (so a copy outlives a deleted
  original, and ink saved on the original is removed from the copy), then deleted pages go, the rest are put in the document's
  order with `move_pages`, blank pages are inserted, and our ink is rewritten on the pages that changed. Pages deleted before a
  save cannot be undone (the file no longer has them): saving forgets those steps and the graves.
* **The test of it**: `pages::tests` (every variant, every inverse), `ink::store::tests` (strokes follow, undo restores order),
  `doc::tests` (files saved and reopened after moves, deletions undone, copies, mixed sessions, no doubled ink), editor tests
  (links, outline, selection) and a storm that moves, deletes, duplicates and undoes pages at random with the document and
  the editor checked page by page after every step.

### The pages overview

A modal card (like the prompt: while it is up every device talks to it and to nothing else) with a picture of every page, its
number, the PDF's table of contents on the left when there is one, and an edit mode.

* `toolbar/overview/layout.rs` — where everything is for a window and a scale (pure; the grid is arithmetic, so a million
  pages cost what three do); `draw.rs` — what it looks like, as plain data in `toolbar::Ui` (panels, lines, and now `Image`s
  and `Label`s). Anything half scrolled out of the grid is cut at its edge or left out.
* `editor/overview.rs` — its state (scroll, folded entries, chosen pages, a drag, an open menu) and what every device does:
  taps, drags (a pen or mouse carries a page; a finger scrolls), the wheel, keys, shortcuts. Page changes while it is up are
  followed (`overview_follow`), and so are window changes (`overview_settled`).
* `app/overview.rs` + `gpu` — text becomes bitmaps (as typed text does), pages become small renders (`tiles::Key::Thumb`), and the
  GPU has a layer between the interface's panels and its lines for both, and draws a page's ink into its picture from the same
  buffer as the document's (a transform and a scissor rectangle per picture).
* `outline.rs` — the table of contents, read with `pdfcraft_organize::bookmarks`, flat, with `visible` (folding) and
  `section_of` (the entry that holds a page).

## Extensions: tools the program does not know

* `tool::Tool` is a **name** (`Tool::Pen`, `Tool::Select`… are constants; an extension's is `Tool::named("laser")`), and `tool::Registry` lists the
  tools in the toolbar's order with the icon of each extension's. The toolbar lays itself out from a registry (`Toolbar::layout_for`), the
  mark of the tool in use slides along its tools, settings find a tool by name (a name left by an extension that is gone is no tool: the pen).
* `inkpdf-api` is the whole of what an extension sees: events, `Context`, `Painter`, `Tool`, `Extension`. `inkpdf-ext` holds the extensions, one
  folder each, found by its `build.rs`. The program depends on both; **an extension depends only on the API**, so the compiler keeps it out
  of the program's insides, and `architecture.rs` checks its dependency list (reviewed by the owner), that it touches no file or network, and
  that the API has no dependencies.
* `tools/ext.rs` is the one place that turns the program's events into the API's and the workspace into the API's `Context`; `ToolSet`
  holds the program's own tools as fields and an extension's as a list (`ExtTool`), and the frame loop asks them `tick` so that an idle window
  still draws nothing. Every contract test (hostile events against every tool) runs on `Tool::all()`, so a new extension is tested by existing
  tests, and the toolbar's and interface's tests use a reference set of tools so that a new extension changes none of them.
* **Item kinds (E3).** A tool's `item_kinds()` gives the kinds of item the extension makes (`inkpdf_api::ItemKind`). The program keeps an item as a
  stroke with a payload, `Stroke::item` (`ink::Item`: the kind's name and a text only the kind reads), whose points are its box (two corners), so
  **undo, moving, copying, pasting, the lasso, the eraser, the page edits and the copies of pages follow it with no code of the extension's**: it is
  hit like a markup (`Stroke::boxy`). `tools/items.rs` is the registry of kinds (asked once, from `inkpdf_ext::all()`), `InkStore::add_item` and
  `edit_item` (one undo step each) make and change one, and `Context::{add_item, item_at, open_item, move_item, remove_item}` are how a tool
  does it. The kind draws it (`paint`, into capsules, in `app/ink_layer.rs`), says what a search finds (`text`) and writes and reads it as a PDF note
  (`write`, `read`): the seam has `AnnotKind::Note`, `NewShape::Note` and `Reply` (a note with the replies to it, and a review status for "done"),
  written by `ink_io` with the name `inkpdf-item:<kind>:<stamp>`; a note of another program, or of a kind this build has not, stays in the file as
  it is and is drawn by the renderer. The conformance suite has `check_notes`.
* **The card of an item.** An item's kind may have a card (`ItemKind::card`, `act`): rows of text, a field to write in, buttons of the kind's own and
  the program's delete. It is the same card for every kind (`toolbar/item_card.rs` lays it out and draws it, `editor/item_card.rs` holds its state in
  `Workspace::card`, takes its keys and presses): at the right under the bars (and under the search card), not modal, the keyboard its own while it is
  open, every part a button for a stylus tip or the left mouse button, Enter to send, Esc to put it away, Delete in an empty field to delete the item.
  The name written on what is sent is a setting (`author`; the shell offers the system's user name until one is chosen).
* **The sticky notes** (`inkpdf-ext/src/notes/`) are the first kind: a click or a tap puts a note, a click on it opens its thread, a drag moves it. In a
  PDF a note is a text annotation with replies, so every reader shows the thread; "done" is the review status Completed. The row of
  `editor/tests/notes.rs` is the notes' place in the capability matrix.
* How to write one: `docs/EXTENSIONS.md`; to make one: `tools/new-extension.sh`.

## Text: read behind the frame, kept by file page, selected and searched

* **Reading.** `pdf::TextSource` (one per thread: the file stays parsed between pages) gives a page's text as a `PageTextView`
  (`pagetext.rs`: glyphs in reading order, boxes, words, lines, find; `FakeText` is its grid-of-letters stand-in for tests). `indexer.rs`
  (adapter) runs one on a thread of its own, takes wishes ("these pages, most urgent first": the shell asks for those nearest the page in
  view) and hands pages back, which `app/frame.rs::stream_text` gives to the editor. It reads the file as the renderer has it, without the
  ink and the text boxes the program keeps itself (those are searched from the ink store, so nothing is found twice).
* **Keeping.** `doctext.rs` (model) holds what was read by *page of the file*, and which page of the file draws each page of the document
  (the shell updates the second when pages are edited), as the pictures are kept: a page edit reads nothing again, a copy shares its
  original's, an added page has none. `Workspace::text` is that; a selection holds the page's text it was made from and lets go if the page
  has another by then.
* **Markup.** A text markup is a `Stroke` with `markup: Some(kind)` whose points are the opposite corners of the boxes it marks, so the
  store's undo, selection, move, copy, erase and page-edit code is the same as for any stroke. `ink_io` writes it as a Highlight,
  Underline, StrikeOut or Squiggly annotation (boxes of one kind and colour that follow one another are one annotation, with the corners
  as a reader writes them) and reads back those that carry our name; the renderer does not draw them (the ink layer does, as capsules).
* **Select** (`tools/select.rs`) is one tool like the others: a press on a letter, a drag, double and triple presses, handles at the ends
  (the only way for a stylus tip to stretch a selection), the keys; its bar is the bar under the tools (copy, delete, and its marks as the
  tool's own actions, `ToolAction::Mark`). **Search** (`editor/search.rs`, drawn by `toolbar/search_card.rs`) is not modal: the card floats
  at the right, the keyboard is its while it is open, and the places are worked out again whenever the query, the options, the text read so
  far or the ink changes; they are lit over the page by `app/ink_layer.rs::search_overlay`.
* The interface had no text of its own before the search card: its labels now go the way the overview's do (bitmaps drawn between the
  panels and the lines), kept while the interface is not rebuilt.

## Colour: roles, two looks, and the page's own colours

* `palette.rs` (base) is every colour of the interface by the job it does (`Palette`: panel, ink, accent, the washes, danger, selection,
  the paper of the overview, …). `LIGHT` has exactly the values the program always had (a golden test, `editor/tests/golden.rs`, hashes
  what fifteen scenes draw and fails if the light look changes); `DARK` is the same roles on a dark slate, with contrast tests for both.
  `Palette::mix` makes the colours in between, which is how the look fades.
* A drawing function reads colours from `ui.pal` (the interface) or `ws.theme` (the tools' handles, guides and selection): never a
  literal. `architecture.rs` fails if a colour literal appears in `toolbar/` or `tools/`. `Ui` carries the palette it is drawn in, and
  the shell's `UiStamp` holds it, so the interface is rebuilt on the GPU while the look fades and not otherwise.
* Which look: `settings::Appearance` (system, light, dark) and the system's (`Platform::color_scheme`, read at start, when winit says it
  changed and when the window gains focus; Windows from winit's `Window::theme()`, Linux from `gsettings`, Android not yet) resolve to a
  `Scheme` in `editor/appearance.rs`; `Motions` owns the fade (one `Tween`; reduced motion: instant).
* The pages are not the interface's colours. With dark pages on and the look dark (`Workspace::dark_pages_active`), `pdf::PageLook::Dark`
  makes the pdfcraft pool render with reading colours (`DARK_PAPER`, `DARK_TEXT`); `Doc::set_look` builds a new pool, and the shell drops
  the old pictures. What the user drew (ink, shapes, typed text) is shown through `palette::on_dark_page` (lightness turned over, hue kept,
  lifted until it can be read on the paper) at the few places that build capsules and text bitmaps (`Workspace::on_page`); the stored colours
  are never touched, so a saved file is the same with the look on or off (a test).

## Motion: time lives in one place, drawing stays time-free

Everything in the interface that moves (a button's wash, a press spreading, the mark of the tool in use sliding, the bar and
the tool panel coming in and folding up, the prompt, the pages overview coming in, going out and its pages sliding after an
edit) is made of the same few pieces:

* `motion.rs` (base: it depends on nothing) — `Curve` (Material's standard, decelerate and accelerate), `Tween` (a value that
  goes to a target over a time and, given a new target on the way, from where it has got to; saying the same target again
  does not start it over), `Presence` (kept while it goes out, so that it can be drawn so after the state it came from has
  moved on), `Slides` (things away from where they belong, going there), `Prefs` (reduced motion: every duration nothing).
  Time is an argument and a step is capped, so every animation is a test.
* `editor/motions.rs` (session) owns every animation in one registry (`Motions`), is told where things are heading once a
  frame (`Editor::step_view` → `step_motions`) and says whether anything is still moving; the shell asks for another frame
  only then, so an idle window still costs nothing. The values it hands out are plain numbers.
* `toolbar` (ui) draws from those numbers and knows nothing of time: `Look` for the buttons (`Look::resting` is what a state
  settles to), `PageMotion` for a page's picture in the overview. `scene::Xform` (scale about a point, a shift, a fade) is put
  over a group of what was drawn with `Ui::mark` / `Ui::apply`, which is how things come in, go out and slide without the
  drawing code changing.
* The shell (`app`) keeps what a thing was drawn as while it goes out (the overview's `ghost`) and reads the Windows
  "animations" setting (`Platform::motion_prefs`; `INKPDF_MOTION=off|on` overrides it for a run).
* Tests run with reduced motion (what they look at is where things end up); `editor/tests/motions.rs` and the overview tests
  turn it on and drive the frames. `stress_motion_changes_how_long_things_take_and_never_where_they_end_up` runs the same
  random events with motion off and on, letting everything arrive after each, and requires the same document, selection and
  overview; the hostile overview storm runs with motion on and frames of every length (zero, negative, not a number, five
  seconds) and requires every moving value to be a number within its ends.

## SOLID, concretely

* **S** — `Tool`s (one interaction style each), `InputPolicy` (who may do what), `Workspace` (shared
  document state), `Requests` (asks of the shell), `Editor` (routing + chrome).
* **O** — a new tool is one file implementing `Tool` plus one variant in `ToolSet`'s two `match`es. The
  shell names no tool type (checked by a test).
* **L** — every tool honours the contract suite (`contract.rs`): idle when new, owns only what it began,
  cancel leaves the document untouched, end/settle/leave are idempotent, devices outside the policy never
  reach it, and 4 000 hostile events leave it sound.
* **I** — a tool sees `Workspace` (not the editor), `Painter` (not the GPU), and may ask the shell only
  through `Request`.
* **D** — the renderer depends on `Painter`/`Tool::paint`, not on any tool's internals.

## Patterns

| Pattern | Where |
|---|---|
| **Strategy** | `Tool` objects; `InputPolicy` as per-tool data |
| **State** | each tool's private gesture enum (`Draw`, `Drag`, `Control`, `DraftTap`, `Place`, `Grab`…) |
| **Command** | `ink::Cmd` — the undo log |
| **Facade** | `Editor` |
| **Registry** | `ToolSet::get/get_mut` (total: no `Option`) |
| **Observer (queue)** | `Request` queue drained by `app::files::service` |
| **Composition** | `Mover`, `Eraser`, `Lasso` held by Pen and Shape (and `Mover` by Text) |
| **Flyweight** | text bitmap cache (kept) |
| **Builder** | `Draft`, a polyline built node by node (kept) |
| **Incremental computation** | the live stroke's smooth curve is extended segment by segment (`curve_segments`) |
| **Ports & Adapters** | `platform` (`Platform`, and a `PointerSource` per OS → `PointerEvent`), `store` (`FileStore`, with `path_store`), `gpu` (scene → wgpu), `Painter` |

## Modes and device rules (`Tool::policy(mode)`)

The rules depend on a `Mode`, which follows the machine's posture (`src/posture.rs`):

| Mode | When | Mouse | Keyboard |
|---|---|---|---|
| **Desktop** | not in slate posture, or not a machine that has one (every desktop PC) | stands in for a stylus on the pen, shape and pointer tools; text as itself | shortcuts (Ctrl+Z, Ctrl+Y, Ctrl+Shift+Z, Ctrl+S, Ctrl+A/C/X/V/D), the selection's keys and typing |
| **Tablet** | the OS reports slate posture on a portable machine with a touch or pen digitizer | scrolls only | typing (physical or Windows' touch keyboard), no shortcuts |

| Tool | Stylus | Mouse (desktop) | Mouse (tablet) | Touch | Keyboard |
|---|---|---|---|---|---|
| Pen | draw, erase (eraser end), lasso (barrel) | as a stylus: left tip, right eraser end, middle barrel | scroll | pan/zoom | desktop: the selection's keys |
| Shape | select, draw, erase, lasso (tap-drawn polylines and splines) | as a stylus | scroll | pan/zoom | desktop: the selection's keys, Backspace on a point |
| Lasso | tip loops or taps, picks any kind of item, drags what is picked | as a stylus | scroll | pan/zoom | desktop: the selection's keys |
| Eraser | tip erases any kind of item | as a stylus | scroll | pan/zoom | none |
| Pointer | point | as a stylus (dot follows the mouse) | scroll | pan/zoom | none |
| Text | desktop: none; tablet: place/select/move text | place/select/move text | scroll | pan/zoom | types, caret, selection |

Every device still presses the window's chrome (toolbars, panel, prompt, the bar under the tools); the wheel
always scrolls.

### Create, select, move, restyle, copy, erase, delete: whatever the device

The promise: with a tool chosen, every item it made supports all of those, with only the devices the mode
guarantees (desktop: left button and keyboard; tablet: the stylus tip). `editor/tests/capability.rs` states it per
tool and mode and runs it through those devices alone; the stylus's barrel button and eraser end and the mouse's
right and middle buttons are shortcuts and no test may need them.

* **Role** (`input::Role`: draw, erase, lasso) is what a press does. `Workspace::role` is the one place that combines the pen's own
  buttons (a held button wins) with the tool: the lasso tool's plain tip is a lasso, the eraser tool's an eraser, any other tool's a draw. So
  the stylus's eraser end and barrel button erase and loop with every tool that makes items (the pen and shape tools in `down`, the text tool
  in `press_at`), and the two tools are the same gestures with the tip alone.
* **The selection's operations** live once, on the workspace (`selection.rs`): select all, delete, duplicate,
  copy, cut, paste, nudge, restyle. Each is one undo step (`InkStore::add_copies`, `replace_many` with its
  `Cmd::Restyle`, which coalesces a slider drag into one step). Keys, shortcuts and the buttons of the bar call
  these; nothing is implemented twice.
* **Tool scope** (`selection::Kind`): selecting, erasing, select-all and paste only touch the tool's own kind of
  item (handwriting, shapes, text boxes), so tools stay independent and a loop cannot grab what another tool made. The exceptions are the
  lasso and the eraser (`Tool::picks_any`), whose job is every kind.
* **The bar** (`toolbar/context_bar.rs`, `editor/context.rs`): buttons for the selection operations, the
  points of the shape being edited (`selection::NodeAction`, done by `ShapeTool::node_action`, the same edits the
  barrel button and a double tap make), the five colours, and the settings button. It is a chrome interaction
  (`Act::Context`) like the toolbar's, so every device presses it. The tool's panel is not a separate pop-up: it
  unfolds from the bar (`ContextBar::draw` draws bar and panel as one card; `Editor::drawer` is the card's rectangle
  for hit testing, where a press does nothing), and a tool's own button only chooses the tool. On a window too narrow
  for five colours they are one dot that opens the panel (`ContextBar`'s `compact`).
* **Keys** reach a tool as `tools::Key`. `tools/shortcuts.rs::selection_key` (Delete, Escape, arrows) is shared by the
  pen, shape and text tools; Ctrl+letter shortcuts are the session's (`Editor::shortcut`, desktop only) and go to
  the text tool as `Key::Chord` while a box is being edited.
* **Text editing** is `TextEdit` (text, caret, selection anchor) in the text tool plus pure layout in `text/layout.rs`
  (`caret_at`, `index_at`, `vertical`, `selection_rects`, `follow_wrap`). The system clipboard is a domain trait
  (`clipboard::TextClipboard`) held by the workspace; `Platform::clipboard` gives the system's (Windows: `platform/windows/native.rs`), and tests use
  the in-memory one.

How it fits the layers: a tool states a `Tool::policy(mode)` (an `InputPolicy` with a `MouseUse`: `Scrolls`,
`Itself` or `AsStylus`) and never learns the mode. The editor's router hands a mouse to a stylus tool as a
stylus with an id of its own, so no tool has a mouse code path. The mode is the session's (`Editor::set_mode`
ends whatever was under way first); the shell sets it from `posture::detect()` at start and again when
Windows sends `WM_SETTINGCHANGE` "ConvertibleSlateMode", unless `--mode desktop|tablet` forced it. The toolbar's
`Item::ModeSwitch` (right pill, left of full screen) both shows the mode (`State.mode`: a monitor, or a tablet in
the accent colour) and flips it through the same `set_mode`; it is not saved, and a posture change decides again.

`SM_CONVERTIBLESLATEMODE` alone cannot be trusted: an ordinary desktop PC reports 0 ("slate"). So `posture::decide`
also needs a touch or pen digitizer and a platform role of mobile or slate (`PowerDeterminePlatformRole`). The
rule is a pure function with a test per kind of machine; the flip itself cannot be tested without a convertible.

## Latency (input → pixels)

1. **Late sampling**: wait for the display (`Gpu::acquire`), *then* drain the pointer queue.
2. **Prediction**: the live stroke is extended 12 ms from the last samples.
3. **Incremental curve**: a frame re-smooths only the last few segments of the live stroke, not all of it
   (proved equal to smoothing it whole, `smooth::tests` and `editor::tests::pen`).
4. **No per-frame allocation of the overlay buffers**: they are owned by the shell and reused.
5. **Pen-down frames do not wait for tiles**: uploads are capped at 1 ms (4 ms otherwise).
6. **Incremental GPU appends** for committed ink.

Measured with the synthetic pen (`inkpdf --stats`, 830–860 frames): pen sample → frame submitted
p50 2.6–2.8 ms, p95 4.3–4.4 ms, against 2.5 / 4.4 / 11.1 ms before the rewrite. The newest sample is
already 2.8 ms old when the frame reads it, so the frame's own work adds ~0: what remains is the input
delivery and the display clock, not code that can be sped up here. The p99 swings between runs (11–14 ms)
with whether a frame lands on a vblank boundary.

## Testing

* Domain: unit and property tests.
* Tools: behaviour tests through `Editor` (`editor/tests/*`) and the contract suite.
* Architecture: `src/architecture.rs` fails if the domain imports tools/editor/adapters, a tool imports
  the editor, the toolbar, an adapter or another tool, the session imports the GPU/shell, or the shell names
  a tool type (shown to fail on a real violation).
* Stress: seeded storms (all tools, undo, pages, save/reopen) at `INKPDF_STRESS=10`.
* Real input (`tools/e2e/`, `run.ps1`, about half a minute): two scripts drive the built exe, in four app starts in all,
  with a synthetic stylus and finger, the real mouse and keyboard, and check pixels and the title. They prove only
  what the other tests cannot see: that each device reaches the app and does its work, that the tools draw on the
  screen, that pages and the saved file come out right, and that the mode button and the posture message work.
  The rules themselves (every device in every tool and mode, every edge) are the unit and stress tests' job.
  Known limit: Windows' synthetic pen injector drops the eraser flag on this OS build, so the eraser end is
  covered by the unit and stress tests only.
